# 身份、ACL 与同步设计基线

## 文档目的

本文定义云程研 App 在进入数据实现前必须遵守的身份、安全边界与本地优先同步原则。本文只记录设计边界，不配置 LeanCloud，不定义可直接实现的 LeanCloud 类、字段或 ACL，也不选择具体服务端实现。

本文用三种状态避免把建议误当作决策：

- **已确认**：可作为后续设计和实现的约束。
- **推荐但待批准**：候选方案，用户批准并写入决策记录前不得作为实现依据。
- **待决**：信息或选择不足，必须在实现前由用户明确决定。

## 已确认

### 产品与技术边界

- 产品仅供三人私用，不提供公开注册；APK 私下分发。
- 负责人在线下预置三枚一次性邀请码。客户端不提供邀请码创建、查看、补发、撤销或其他管理页面。
- 技术基线为经典 uni-app（不是 uni-app x）、Vue 3、TypeScript、Pinia、LeanCloud 与本地优先。
- 固定依赖方向为 `Page → Feature / Use Case → Repository → Mapper → Platform Adapter`。
- Page 不直接调用 LeanCloud 或 `uni.*`。LeanCloud SDK 对象、查询对象和错误类型不得越过 Repository/Mapper 边界；设备、文件、网络和本地存储能力通过 Platform Adapter 暴露。
- 同步由基础设施承担，Page 只表达用户意图和展示状态，不查询远端 SDK、不遍历待同步记录，也不编排重试或冲突解决。
- 当前阶段没有 LeanCloud 配置，没有 appId、appKey 或 MasterKey，没有用户数据，也没有包名/AppID。真实凭证、用户数据和 MasterKey 不进入客户端、仓库、日志或 CI 输出。

### 身份生命周期

1. **预置**：负责人在线下预置三枚一次性邀请码；具体预置工具和受控运行环境尚未选择。
2. **首次注册**：用户提交一枚邀请码。只有兑换成功后，用户才可设置昵称与账号密码。
3. **邀请码消耗**：每枚邀请码只能成功兑换一次。兑换成功后不能再次用于注册。
4. **日常使用**：注册完成后保持登录；应用日常启动不重复要求邀请码。

“保持登录”不等于客户端永久拥有授权，也不替代服务端验证。会话保存期限、撤销、换机、密码恢复和重新认证规则仍待决定。

### 邀请码兑换的信任边界

邀请码兑换必须由服务端或其他受控基础设施原子执行。一次成功兑换在同一受控操作中至少要保证：校验邀请码可用、阻止并发重复兑换、建立或绑定唯一身份、将邀请码标记为已消费；任一步失败时不得留下可重复使用的邀请码与已创建身份之间的不一致状态。

客户端只负责提交兑换请求和展示结果，不得自行判定邀请码真伪、消费状态、身份权限或 ACL，不得持有能绕过上述检查的高权限凭证。重放、并发请求或网络重试不能产生第二个成功身份。这里规定的是架构约束，并不要求本任务选择、部署或模拟具体的云函数、服务进程或管理工具。

### 本地优先与同步职责

- **读取**：应用的首要可用数据源是本地数据。Feature / Use Case 通过 Repository 读取本地投影，不因远端暂时不可用而阻塞已有本地内容的展示。
- **写入**：业务写入先形成可恢复的本地结果，再由基础设施识别并同步尚未确认的变更。何时可向用户宣告“仅本地保存”或“已同步”由后续状态模型决定。
- **同步**：基础设施负责网络状态感知、出站变更、入站更新、重试、远端确认与同步状态持久化；Repository/Mapper 隔离 LeanCloud 表示，Platform Adapter 隔离网络和持久化能力。
- **页面职责**：Page 可触发用例并展示领域化结果或同步状态，但不得调用 LeanCloud SDK、直接调用 `uni.*`、拼装远端查询或决定冲突胜负。
- **冲突**：当前没有获批的同步冲突策略。实现不得用“最后写入获胜”、本地优先覆盖、远端优先覆盖或静默合并等默认行为掩盖这一待决项。

### 离线业务约束

- 已存在的本地数据在离线时仍应作为首要可用来源。
- 每日打卡由用户手动执行，每日一次，内容为状态与可选的 0–140 字文字。
- 正计时专注少于 1 分钟不保存。
- 日、周、月统计依据本地完成时刻；每周按周一至周日计算。
- 已保存记录的时长不可编辑；创建者可在确认后删除。

以上业务规则确定了本地校验和后续同步必须保持的语义，但尚未决定离线重复打卡、跨设备并发、删除传播或设备时钟异常的冲突结果。

### 最小权限目标

- 默认拒绝未认证访问；每项读取、创建、修改、删除和管理能力都应有明确授权依据。
- 普通客户端只获得完成已批准产品用例所需的最低权限，不获得邀请码管理、批量用户管理、绕过 ACL 或读取系统秘密的能力。
- 邀请码兑换与任何提升权限的操作只能在受控基础设施内完成；MasterKey 等高权限秘密永不下发客户端。
- Repository 返回领域/应用类型和可处理错误，不泄漏 LeanCloud SDK 对象或特权实现细节。
- 创建者确认删除这一业务权利需要由远端授权机制强制执行，不能只依赖客户端隐藏按钮或本地校验。
- 三名用户彼此可见的数据范围尚未获批；在范围明确前，不得假设“私用”意味着三人可以读取或修改彼此全部数据。

## 推荐但待批准

以下建议均未获批准，不构成 LeanCloud 配置或实现规格。

### 身份与离线会话

- 首次邀请码兑换和无有效会话时的账号登录需要连接受控基础设施；客户端离线时不自行完成注册或验证账号密码。
- 在本地存在仍有效且未被明确撤销的会话时，允许用户离线进入应用并使用已缓存的自身数据；恢复网络后再由身份基础设施校验和刷新会话。
- 通过 Platform Adapter 保存会话材料，并只保存 SDK 正常恢复会话所必需的最少信息；日志和诊断报告只记录脱敏状态。
- 将退出登录、会话失效、密码变更后的本地数据保留或清除设计为显式用例，避免用清缓存等隐式行为处理身份切换。

### 同步运行方式

- 用持久化的同步状态记录本地变更是否待发送、发送中、已确认或需人工处理，使进程退出和网络切换后仍可恢复。
- 为可重试写入提供稳定的操作标识，并要求受控基础设施具备幂等语义，避免超时重试形成重复记录。
- 将同步触发限定为应用启动/恢复、网络恢复、本地写入后和用户明确刷新等基础设施事件；采用有限并发与退避，不由页面循环轮询。
- 删除先保留可同步的删除意图，直到远端确认后再按获批保留策略清理；是否采用墓碑以及保留多久仍需随数据模型批准。
- 向 UI 暴露领域化状态，例如“仅本地”“同步中”“已同步”“需要处理”，但具体状态集合与用户操作须在模型确定后批准。

### 安全与可审计性

- 邀请码只保存不可逆验证材料而非可直接读取的明文，并限制兑换尝试频率；具体算法、限流位置和审计保存期在选定受控基础设施后决定。
- 对登录、邀请码兑换、会话撤销和拒绝访问保留最小化审计事件；不得记录密码、完整邀请码、会话令牌或用户正文。
- 在 ACL 设计时按“资源所有者、允许的协作者、受控服务”分别枚举能力，逐项证明普通客户端不具备管理权限。

## 待决

以下事项必须由用户批准并写入决策记录后，才能形成实现规格：

### 数据模型

- LeanCloud 类名、字段名、字段类型、必填性、默认值、索引、唯一性与校验规则。
- 身份、用户资料、邀请码、打卡、专注记录及同步元数据之间的关系和所有权表达。
- 本地记录标识与远端标识的映射、模式版本、迁移策略、删除表示和数据保留期限。
- 本地完成时刻的持久化格式、时区/设备时钟异常处理，以及统计跨时区或改时钟后的语义。

### ACL 与可见性

- 三名用户能否看见彼此的昵称、打卡、专注记录和统计，以及是只读、可评论还是可修改。
- 每类资源的创建、读取、更新、确认删除权限；普通用户、资源创建者与负责人是否需要不同角色。
- 邀请码预置和兑换采用何种受控基础设施，以及该设施如何获得和隔离所需权限。
- 使用对象 ACL、角色、受控函数或其组合的具体 LeanCloud 授权方案及拒绝路径测试。

### 冲突与同步

- 同一用户、同一天、多个设备离线打卡后的唯一性与保留结果。
- 专注记录的重复提交、创建与删除并发、删除后离线重放、远端不存在及部分失败处理。
- 不同实体采用本地优先、远端优先、版本比较、人工选择或其他策略的逐项规则；不得以一个全局默认替代逐实体决定。
- 时钟偏差、版本号/修订号、幂等窗口、重试上限、退避、同步批量大小、初次拉取和增量游标设计。
- 同步状态、失败提示、手动重试入口、诊断信息及本地队列保留期限。

### 身份运维

- 账号标识规则与唯一性、昵称重复策略、密码策略和错误提示。
- 会话有效期与刷新、退出登录、远端撤销、换机、密码修改/找回及账号不可用时的恢复流程。
- 三枚邀请码的生成、线下交付、过期、撤销、丢失和误用处理；客户端仍不提供管理页。
- 最小化审计事件、保存期限、可访问人员与清理方式。

## 后续批准门

1. 用户先批准数据资源及彼此可见性，再批准逐资源 ACL 权限矩阵。
2. 用户批准身份运维与邀请码受控执行方案，且确认客户端不承担信任边界。
3. 用户按实体批准离线冲突、删除和重复提交规则。
4. 以上决策写入项目决策记录后，才可创建 LeanCloud 映射、Repository 实现、同步状态机或相关测试。

在这些批准完成前，本文只能用于评审架构边界，不能被解释为已完成的后端设计或安全配置。
